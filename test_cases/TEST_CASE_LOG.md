**Standing per-task pattern (decided 2026-10-20):** each task is delivered as one zip with full apply/build/test/commit/push instructions, followed by one or a small handful of quick smoke-check test cases to run right after building. This repeats for every task through the last one.

**Standing test-strategy convention (decided 2026-10-20, supersedes the earlier Postman/manual-login smoke-check approach):** Talha has one phone and already wiped his test accounts, so recreating a linked Guardian+Dependent pair per task to manually test is too slow to repeat every task. - What this does *not* catch, and stays deferred to one full team pass before final submission: real on-device rendering (map tiles, actual GPS), true multi-account flows (Secondary permission gating, invite acceptance), and anything needing real OS-level behavior — background services, push notifications, real calls, real GPS/permission dialogs. Flagged explicitly, task by task, whenever a widget test alone gives weaker confidence than usual because of this.

**Standing delivery convention:** before any manual "run the app" step, or before handing Talha a smoke-check, Claude confirms the backend is currently running and gives the exact restart commands if not — `cd D:\humsafar\backend` → `.\venv\Scripts\Activate.ps1` → `uvicorn app.main:app --reload`, in its own terminal, kept separate from the Flutter terminal.

**Standing research convention (added 2026-10-20):** before building each task, Claude pulls the latest `mabdullahghafoor/humsafar` `dev` branch fresh and re-reads the actual contracts/mockups — never from memory — since Abdullah and Sarim push updates frequently.

**Standing multi-task-batch convention (added 2026-10-20, starting with 3.11+3.12):** when Talha asks for more than one task in a single delivery, each task still gets its own section below with its own test IDs, its own named scope decisions, and its own entries in "Open cross-cutting items" — batching the zip doesn't batch away the per-task bookkeeping.

**Standing test-writing conventions (added 2026-10-22, after triaging a 13-test regression across Tasks 5.6–6.8 — see those sections below for the full root-cause breakdown):** four gotchas kept recurring across those test files and should be designed around in every new widget test from here on:
1. A screen that calls `Navigator.of(context).pop(...)` on a successful save/pair/confirm (which is most of them) must be reached in the test via `context.push(...)` from a second route — never set as GoRouter's sole `initialLocation` — or that `pop()` empties go_router's match list and throws `'currentConfiguration.isNotEmpty'`. Use the `AutoPushHost` helper now in `test/support/widget_test_harness.dart` (`initialLocation: '/host'`, routes = `[GoRoute('/host', ...AutoPushHost(targetPath: ...)), ...realRoutes]`).
2. `find.widgetWithText(ElevatedButton, '...')` / `OutlinedButton` does **not** match a button built with the `.icon(...)` factory constructor — Flutter's `find.byType` matches by exact runtime type, and `.icon()` returns a private subclass. Match with `find.ancestor(of: find.text('...'), matching: find.byWidgetPredicate((w) => w is ElevatedButton))` instead — covers both the plain and `.icon` forms.
3. Every screen's AppBar carries a `PopupMenuButton<String>` language switcher (`language_switch_button.dart`) alongside any menu the screen itself adds — an untargeted `find.byType(PopupMenuButton<String>)` is ambiguous almost everywhere. Scope it, e.g. `find.widgetWithIcon(PopupMenuButton<String>, Icons.more_vert)` (the screen's own menu keeps the default icon; the language switcher uses `Icons.language`), or `find.descendant(of: ..., matching: ...)` for a per-row menu.
4. A plain `ListView(children: [...])` only builds the children currently near the viewport — same lazy behavior as `.builder`, not "all children exist because I passed a literal list." A widget below the fold isn't in the Element tree yet. Scroll it in first: `await tester.scrollUntilVisible(finder, 200, scrollable: find.byType(Scrollable).first);` before asserting on or tapping it.

## Task 4.7 — Voice/video call UI + ZegoCloud integration

Delivered as its own isolated commit, per the roadmap's explicit flag that this is the project's first native-SDK integration and shouldn't be batched with anything else (the same "isolate the native-SDK integration into its own delivery" reasoning Task 6.9 named when it deferred real ZegoCloud video rendering). New `OutgoingCallScreen`, `IncomingCallScreen`, and a thin `CallScreen` wrapper around `zego_uikit_prebuilt_call`'s `ZegoUIKitPrebuiltCall` widget, plus a `showCallTypePicker` bottom sheet. Reached from a new Guardian-only Call button on `ChatScreen`'s AppBar and on `DependentDetailScreen` (right after Message, before Camera) — both skip straight to `OutgoingCallScreen`, not through `ChatScreen`. Incoming calls arrive as a push notification (`type: incoming_call`), intercepted in `main.dart`'s `_handleNotificationTap` ahead of the existing generic notification router, via a new pure function `incomingCallPushData` in `push_service.dart`.

**Named field-name caveat, flagged for Abdullah/Talha to confirm against the real `call_contract.md`:** same standing caveat as Tasks 6.9 and 7.3 — built from the written contract summary in `Humsafar_Progress_Tracker.md`, not a fresh read of the contract file itself (backend repo, not available in this environment). Assumed shapes:
- `POST /calls` with `{"receiver_id": string, "type": "voice"|"video"}` → `{"call_id": string, "status": "ringing", ...}`
- `GET /calls/{id}` (polled every 2s while ringing) → `{"call_id": string, "status": "ringing"|"accepted"|"declined"|"missed"|"ended", "zego": {"app_id": int, "token": string}?}` — `zego` is only present once the call is `accepted`.
- `POST /calls/{id}/accept` → same shape as the GET above, with `zego` present.
- `POST /calls/{id}/decline`, `POST /calls/{id}/end` — no assumed response body; both calls are fire-and-forget/best-effort on the client (a failure here never blocks the UI from popping).
- The backend is assumed to mint the ZegoCloud `app_id`/`token` server-side per call, reusing Task 4.4b's `CALL_PROVIDER=zego` real-token infrastructure — the ZegoCloud Server Secret never ships inside the Flutter client, only this short-lived per-call token (`token`, not `appSign`, is what `ZegoUIKitPrebuiltCall` is given).
- The `call_id` returned by the backend is assumed to double as Zego's own `callID` directly — no separate mapping.

If the real field names differ, only `OutgoingCallScreen`/`IncomingCallScreen`'s HTTP-handling methods need adjusting — `CallScreen` itself only consumes whatever `app_id`/`token`/`call_id` values those two screens hand it, not the contract's shape directly.

**Why not ZegoCloud's own Call Invitation UI kit:** Zego ships a separate, more batteries-included "Call Invitation" layer (ringing UI, push-triggered auto-answer prompts, etc.) on top of the plain `ZegoUIKitPrebuiltCall` widget used here. That layer assumes Zego's own push-notification plumbing wired in parallel with Firebase, which this app doesn't have — this delivery instead reuses the app's existing FCM pipeline (`push_service.dart`) to deliver the "someone is calling" signal, and builds the ringing/accept/decline UI as plain Flutter screens (`OutgoingCallScreen`/`IncomingCallScreen`) that call the backend directly. `ZegoUIKitPrebuiltCall` itself is used only for the in-call UI once both sides have already agreed to join — the one piece with no non-SDK alternative.
